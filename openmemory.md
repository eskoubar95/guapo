# OpenMemory Guide — guapo

This file is a lightweight index of project facts and conventions that are useful to remember.

## Overview
- **Project**: Guapo (DK-first, unisex beauty e-commerce)
- **Focus (MVP)**: face skincare; curation-first guidance; competitive pricing; fast, clean UX
- **Core stack**: Next.js + Medusa + Payload CMS; payments via Stripe (cards, Apple Pay, Google Pay; MobilePay/Klarna when enabled); product subscriptions require recurring billing
- **Repo layout (DECIDED)**: Monorepo with `apps/*`:
  - `apps/storefront` (Next.js customer storefront)
  - `apps/commerce` (Medusa backend + worker)
  - `apps/cms` (Payload CMS as its own Next.js app/service; Payload v3+ is Next.js-native)
- **Package manager (DECIDED)**: pnpm (via Corepack); commit `pnpm-lock.yaml` and treat it as the single source of truth.
- **Env var inventory**: `env.example` (names only; no secrets).
- **GitHub repo**: `https://github.com/eskoubar95/guapo` (git remote `origin` uses HTTPS)
- **Branch strategy (DECIDED)**: `staging` = staging, `main` = production. PRs go to `staging`; releases are `staging` → `main`. Config: `.sdd/git-config.json`.
- **Guardrails (TECHNICALLY ENFORCED)**:
  - GitHub Actions PR Policy workflow blocks direct feature → `main` PRs (must come from `staging`)
  - Branch protection on `staging` and `main`: requires PR, approvals, status checks
  - CI checks validate SDD metadata and spec files
  - Commands (`/task/start`, `/task/validate`, `/task/promote`) use `.sdd/git-config.json` for branch resolution
- **Cloud Agent pilot (Cursor Cloud Agents via Linear)**:
  - Linear label: `agent-ok` (Guapo team)
  - Use only for small, isolated tasks (docs, narrow refactors, small scripts, workflow tweaks)
  - Issue must include: Scope + Out of scope + Acceptance + Workspace
  - Delegation constraint: agent opens **draft PR to `staging`** only; no feature PRs directly to `main`
  - Delegation trigger: post a comment starting with `@cursor` + the strict SDD Cloud Agent prompt
- **Task management + MCP**: Linear is the source of truth for tasks during execution (MCP: `guapo-linear`). Supabase ops use MCP: `supabase`.
- **Sprint context**: We use Linear **Cycles** as sprints (Guapo team cycles enabled).
- **Spec set**: root + PRD + architecture + acceptance + sitemap are now created in `spec/`

## Architecture (high-level)
- **Storefront**: Next.js (PLP/PDP, cart, checkout, account, content)
- **Commerce backend**: Medusa (products, carts, orders, subscriptions)
- **CMS**: Payload (static pages, blog/articles, landing pages, nav/footer links, PDP guidance fields, homepage composition via page builder)
- **Payments**: Stripe (recurring required for subscriptions). Guapo provider `payment-stripe-guapo` extends the official Stripe provider: PaymentIntent **amount** comes from Medusa **`input.amount`** (payment collection). When cart totals change (e.g. Shipmondo + fri fragt), **`refreshPaymentCollectionForCartWorkflow`** must run so the collection matches the cart before creating payment sessions — see `sync-free-shipping-promotion` subscriber and storefront payment-session flow.
- **Shipping**: Shipmondo pakkeshop (GLS/DAO/PostNord); priser via `calculatePrice` + **price_bands** / flat i option-JSON; vægt fra context eller DB (`cart_line_item`×`product_variant.weight`). Flat 39 DKK kun fallback uden bands/vægt.
- **Hosting/DB**: Railway for compute (storefront + medusa-server + medusa-worker + payload + redis); Supabase Postgres for DB; Railway Redis for Medusa requirements
- **Supplier**: Qogita (investigation; decision later)

## Patterns
- **Focus styling**: Do **not** use focus rings. Use **active/focus borders** as the focus indicator (especially on inputs). See `spec/07-design-system.md`.
- **Subscriptions (MVP)**: Cycles 4/8/12 weeks, 5% discount on all renewals, minimum commitment 2 deliveries before cancellation. Controls: skip next delivery, pause, resume, cancel (after commitment). Email-only notifications; renewal reminder 3 days before; failed payments: 2 retries over 3 days then subscription on hold until payment method update. Returns/refunds: same 14-day policy as normal orders; opened products not returnable (except defective); partial refunds supported; if a subscription delivery is refunded/returned, subscription auto-pauses until customer resumes.
- **Checkout (MVP)**: Guest checkout allowed for one-time purchases; subscriptions require an account.
- **Messaging (MVP)**: Balanced: curated premium assortment + competitive pricing (no “cheapest” claim).
- **SEO/i18n**: Use `/da/...` and `/en/...` URL prefixes. Structured data at launch: Product, BreadcrumbList, Organization, WebSite+SearchAction, Article, FAQPage.
- **Sitemap/canonical (MVP)**: Single `sitemap.xml`. Filter/search pages canonical to base category (no indexing of filter combinations by default).
- **Homepage CMS**: Use a homepage page builder with **predefined section types** (component library). Editors can reorder sections and edit per-section fields.
- **Homepage dynamic blocks (MVP)**: Max 10 sections. Best sellers = auto (top sold last 30 days). New arrivals = hybrid (auto default + manual override). Routine block uses simple rules (e.g., per skin type).
- **Curation tags (MVP)**: Skin types supported: dry, oily, combination, normal, sensitive. Product tagging is manual/editorial.
- **Curation concerns + routines (MVP)**: Concerns supported: acne, dryness, sensitivity/irritation, redness, hyperpigmentation, dullness/glow. Routine templates: simple per skin type + per concern. Steps: 3-step baseline + optional 5-step variant.
- **Tagging model (MVP)**: Use primary + secondary tags. Products can appear in multiple concerns, but primary concern/skin type drives default sorting and routine/template selection.
- **Routine steps (MVP)**: cleanser, serum, face cream/moisturizer, SPF (AM required) + add-ons: toner, eye cream, face mask (1–2x/week). Order: AM cleanser→serum→SPF, PM cleanser→serum→face cream; 5-step adds toner+eye cream.
- **Routine recommendations (MVP)**: Show up to 3 products per step (1 primary + up to 2 alternatives). Primary uses primary-tag match; alternatives may use secondary tags if relevant.
- **Conflict rule (MVP)**: A product is “conflicting” for a routine if it does not match the routine context via primary or secondary tag in that dimension (skin type / concern). Conflicting products must not be shown as alternatives.
- **Cookie consent + analytics (MVP)**: Cookie consent required with categories necessary/analytics/marketing. Analytics via PostHog (analytics consent). Marketing pixels Meta + Google Ads (marketing consent).
- **Attribution (MVP)**: Store UTM params in checkout/order metadata (and send as PostHog properties).
- **Content ops (MVP)**: Owner-driven and handled ad hoc (no fixed cadence). CMS workflow enforces review before publish.
- **Legal docs (MVP)**: Founders draft terms/privacy/cookies using templates; legal review can follow post-launch if needed.
- **Retention (MVP)**: Keep marketing/tracking data as long as legally permissible under GDPR + consent; exact retention durations TBD.
- **Subscription compliance (DK)**: Treated as a launch acceptance gate (confirm required subscription disclosures and update copy/policies before shipping).
- **Transactional emails (MVP)**: Provider = Plunk (orders + subscriptions).
- **CMS workflow (MVP)**: Draft → Review → Publish. Roles: Admin, Editor, Writer, Support.
- **Reviews (MVP)**: On-site only + pre-moderation.
- **Observability (MVP)**: Sentry + structured logs + uptime + alerts for payment failures and subscriptions on hold.

## Components
- **Subscription Module (M9):** Custom Medusa module in `apps/commerce/src/modules/subscription`. Model: status (active/paused/on_hold/cancelled/expired), cycle_weeks, discount_percent, Stripe customer+payment_method IDs, retry state (retry_count, next_retry_at, on_hold_at). Link: Subscription → Order (1:many). Store API: GET /store/subscriptions, GET /store/subscriptions/:id, POST /store/subscriptions/:id/{pause|resume|skip|cancel}. Admin: Subscriptions list/detail pages, order-subscription widget. Renewal: job subscription-renewal (8 AM), workflow renew-subscription (Stripe off-session charge, create order, link, update next_renewal_at). Retry job (9 AM), expiration job (10 AM, on_hold>30d → expired). Simulation: SUBSCRIPTION_ID=xxx pnpm simulate-renewal.
- **Subscription robustness hardening (M11):** Renewal flow now differentiates Stripe `authentication_required` / `requires_action` from normal failures, stores failure context (`last_failure_reason`, metadata with pending PaymentIntent), and places subscription on hold without burning retries. If charge succeeds but renewal order creation fails, flow attempts immediate Stripe refund and logs recovery. Subscription model now tracks `last_renewal_order_id` for deduplication context. Jobs (`subscription-renewal`, `subscription-retry`, `subscription-expiration`) are paginated and renewal processing runs in bounded parallel batches (5). Admin now includes retry action for on-hold/retrying subscriptions and address editing on detail page; store API has customer self-service routes for updating subscription addresses and rotating payment method via SetupIntent.
- **Subscription renewal shipping parity (M11):** Renewal flow now resolves shipping from Shipmondo option settings (`shipping_option.data`) instead of hardcoded 39 DKK. Source prices are ex-VAT (minor units via `flat_amount_minor` / `price_bands`), then converted to gross with the renewal VAT rate before Stripe charge; order shipping method keeps ex-VAT amount with tax lines. Free-shipping threshold still comes from `guapo-free-shipping` settings for parity with checkout.
- **Subscription renewal VAT + Medusa payment (M11):** `run-subscription-renewal` computes `itemsGrossDkk` from discounted line total + VAT when `is_tax_inclusive` is false (uses initial order tax line rate), passes that gross to `resolveRenewalShipping` for threshold checks, and charges Stripe `itemsGrossDkk + shippingGrossDkk`. After `createOrders`, it runs `createOrderPaymentCollectionWorkflow` + `markPaymentCollectionAsPaid` (amount = charged øre) so Admin shows captured payments. `GET /admin/orders/:id/subscriptions` avoids `order.subscriptions` graph (not on Order entity); it filters `listSubscriptions` by `metadata.order_id` or `last_renewal_order_id`.
- **Shipping vs pakkeshop (M11):** Storefront `usePaymentSession` sets cart `shipping_address` to the customer’s home address (same as billing); pakkeshop stays on `shipping_method.data` (`service_point_*`). Subscriptions store `delivery_data` (JSON) from that method data; renewals pass it as `shipping_methods[].data` on programmatic orders so Shipmondo still gets `service_point_id`. `resolveRenewalAddressesFromCustomer` **does not** replace subscription shipping street/city when `delivery_data` is a pakkeshop payload (or legacy ship≠bill lines): only **contact** fields sync from the customer; billing can still follow profile. Pure home-delivery subs (no parcel payload, same ship/bill) still get full address sync from `listCustomerAddresses`. Admin: widget `order-delivery-info.tsx` (zone `order.details.side.after`); subscription `DeliverySection`. Store `GET /store/orders/:id` exposes `shipping_method_data` for order confirmation pickup copy.
- **Shipmondo sync + fulfillment:** Seed **opretter ikke** længere GLS/DAO/PostNord shipping options eller default `shipmondo_enabled_products`; brug Admin **Tilføj fra Shipmondo** eller `pnpm sync:shipmondo`. **`pnpm cleanup:shipmondo-seed-options`** (`cleanup-legacy-shipmondo-seed-options.ts`) fjerner legacy options med `shipping_option_type.code === pakkeshop`. `applyShipmondoCatalogSelection` henter produkter via **`fetchProductsForCatalogSelection`**: per `carrier_code` på `product_selections`, ellers merge af `GET /products` pr. konto-carrier (`fetchShipmondoCarriers`); **`upsertShipmondoShippingOptions`** returnerer `errors[]` og logger fejl. `runShipmondoSync` appender upsert-warnings til besked. **Admin Levering:** grid med **checkout-switch** (`PUT /admin/shipmondo/enabled`) + **Ret**-modal (`PATCH /admin/shipmondo/options/:id` med `name` + `data.service_codes`). **Priser:** `OptionPriceForm` låser vægtintervaller når `data.weight_intervals` findes (`mergePriceBandsWithWeightIntervals`). `runShipmondoSync` / catalog apply bruger `upsertShipmondoShippingOptions` + `buildServiceCodesForSelection` / `buildServiceCodesFromProduct`. `createFulfillment` uændret (option `data.service_codes` først).
- **Product Reviews (Fase 3 PDP):** Plugin `@lambdacurry/medusa-product-reviews` in apps/commerce (defaultReviewStatus: pending). Storefront: `lib/medusa-product-reviews.ts` (fetchProductReviews, fetchProductReviewStats), `ProductReviewsSection` on PDP (list approved reviews, stats, CTA to review from order history). Plugin store API: GET /store/product-reviews (filter product_id, status=approved), GET /store/product-review-stats (filter product_id). Submit review requires order_id + order_line_item_id (verified purchase); PDP shows CTA "Anmeld fra ordreoversigt" only.
- **Shipmondo pricing unit bridge (M11):** `apps/commerce/src/modules/shipmondo` — pricing logic lives in `lib/pricing.ts`; `service.ts` orchestrates. Provider accepts legacy minor fields (`amount_minor`, `flat_amount_minor`, `price_bands[].amount_minor`) and optional major aliases, but always returns `calculatePrice().calculated_amount` in major units for Medusa cart totals/payment consistency.
- **Free shipping threshold + checkout payment sync (M11):** `apps/commerce/src/subscribers/sync-free-shipping-promotion.ts` (event `cart.updated`) applies/removes shipping-method adjustments so threshold free shipping matches Shipmondo-priced methods. Adjustment rows now include `code` (promotion code fallback `FREESHIPPING`) and description marker `Fri fragt (Guapo)`; subscriber uses a short retry guard when shipping method amounts are briefly zero/missing. After add/remove adjustments, run **`refreshPaymentCollectionForCartWorkflow`** so `payment_collection.amount` follows decorated cart totals. **Stripe provider hardening:** `apps/commerce/src/modules/payment-stripe-guapo/services/guapo-stripe.service.ts` resolves cart data and uses `cart.total` for `initiatePayment` amount when available to avoid stale payment-collection reads in timing windows. **Storefront:** `usePaymentSession` cache guard also keys on shipping data + free-shipping qualification to avoid stale `client_secret`.
- **Commerce shared libs (refactor):** `apps/commerce/src/lib` — `stripe-helpers.ts` (order payment method resolution + card metadata), `subscription-discount.ts` (SUBSCRIPTION-5PCT + product metadata override + renewal discount rules), `container-types.ts` (resolveQuery/Payment/Order/Link), `subscription-renewal/*` (price from initial order, Stripe charge, order payload), `shipmondo-pickup-client.ts` (store pickup proxy), `payload-slug-helpers.ts` (category sync handles). Shipmondo: `lib/shipment-builder.ts`, `lib/label-polling.ts`; fulfillment `productsCache` is per-service-instance; `lib/db.ts` uses a small `pg` **Pool** (max 3) instead of per-call `Client`.
- **Shipmondo fulfillment + webhooks:** `createFulfillment` throws `MedusaError` if API keys are missing (non–dry-run) or Shipmondo returns an error — Medusa then deletes the draft fulfillment. **`product_code`:** Medusa `shipping_option_id` is `so_*`, not a Shipmondo code; `validateFulfillmentData` copies `product_code` from option `id` / `product_code` into cart/order shipping method `data`; `createFulfillment` resolves from fulfillment `data`, then order `shipping_methods[].data`, then DB `shipping_option.data` (same schema as `DATABASE_SCHEMA`). **Parties:** receiver email from `order.email` or `order.customer.email`. Sender address from **stock location** (`location_id`); sender contact from **shipping_profile.metadata** (`sender_email`, optional `sender_name`/`sender_phone`) via `shipping_option_id`, then env `SHIPMONDO_SENDER_*` overrides; `SHIPMONDO_SANDBOX=true` fills gaps. DK postcode normalized to 4 digits. Optional `POST /hooks/shipmondo` verifies HS256 JWT with `SHIPMONDO_WEBHOOK_ENCRYPTION_KEY` and patches Shipmondo fulfillment `data` (tracking, pkg_no) when `reference` matches Medusa order id. Store proxy routes use optional per-IP rate limit (`SHIPMONDO_STORE_RATE_LIMIT_*`). Run `pnpm verify:shipmondo` from `apps/commerce` for API connectivity.
- **Payload Localization (apps/cms):** Built-in localization enabled in `payload.config.ts`: `locales: ['da', 'en']`, `defaultLocale: 'da'`, `fallback: true`. Localized fields: Pages (title, slug, meta, content), Articles (title, slug, excerpt, content, meta), Products (title, keyIngredients, ingredients, beneficials), Navigation (mainMenu, ctaButton), Footer (columns, legalLinks, newsletter, copyright), Homepage (meta, sections), Media (alt). Storefront can request `?locale=da` or `?locale=en`; optional `?fallback-locale=...`.
- **Blog / articles (storefront + CMS):** `GET /api/storefront/articles/by-slug?slug=&locale=` returns one published article (depth 2). Storefront: `fetchArticleBySlug` + `getArticleBySlugCached` (React `cache`), `articleOgImageUrl` in `lib/payload-articles.ts`; `/[locale]/blog/[slug]` renders Lexical→HTML + featured hero. `/[locale]/blog` uses `ArticleFeed` + `ArticleCard` (`components/blog/`) inside `section-container` (featured + grid). Payload **Pages** `pageType: blog-index`: optional rich-text intro + same feed via catch-all `[...path]` (e.g. path `nyheder`).
- **Home sections**: HomePromoBars, CategoryStrip (colored circles), **PromotionSlider** (`components/sections/PromotionSlider.tsx`): horizontal slide with CSS `translateX`, ~700ms easing, autoplay 7s, pause on hover, prev/next chevrons **beside** the banner from `sm` up (hidden on mobile; dots + autoplay there), dots below; i18n `home.promoSlider.previousSlide|nextSlide|goToSlide`. FeaturedProducts, CampaignSection, RoutineBlock, ContentGrid, BrandSpotlight, CtaStrip, ServiceStrip, Newsletter. **Hero marketing art (HTML → export → Payload):** `apps/storefront/design-assets/hero-banners/`. The former Figma/Vite design submodule at `design/Ecommercestorefrontdesign` was removed from the monorepo (see `spec/05-decisions.md`).
- **Storefront cart price display (inkl. moms):** Single source in `lib/cart-display.ts`: `getCartDisplayItemTotalInclTax` (cart total from summed line `subtotal`+`tax` or fallbacks), `getCartPageItemDisplayContext` + `getCartLineTotalOriginalDisplay` / `getCartLineTotalDisplay` / `getCartLineModalUnitPrice` — **same scaling as `CartItemRow`** (raw line totals scaled to `itemTotalInclTaxDisplay`). `CartItems` uses `computeSumRawLineTotalsForCartPage`. Modal, header dropdown, checkout order summary, and full cart page all consume these helpers so PLU line price = cart row = modal unit × qty = «Kurv total» (minus `discount_total` where applicable).
- **Order confirmation unit price display (M11):** In `OrderConfirmationContent.tsx`, `pr. stk.` is derived from line totals (`item.total / quantity` in **DKK major**, same as Medusa store amounts) so the unit price is VAT-inclusive and discount-aware. Do not render raw `item.unit_price` alone when inclusive totals are expected.
- **Transactional order docs + emails (M11):** New subscriber `apps/commerce/src/subscribers/order-placed-transactional-documents.ts` runs on `order.placed` and (idempotent via `order.metadata.transactional.*`) generates two PDFs (`order confirmation`, `invoice`) using `lib/documents/build-order-pdf.ts`, stores base64 payloads in `order.metadata.documents.*`, sends Plunk templates `order_confirmation` and `subscription_created` through `lib/transactional-email/service.ts`, and resolves locale (`da`/`en`) for template copy. Secure customer downloads are exposed at `GET /store/orders/:id/documents/{order-confirmation|invoice}` with ownership checks + rate limit middleware `store-order-documents-rate-limit.ts`; storefront order confirmation shows links when `order_confirmation_pdf_url` / `invoice_pdf_url` are present. HTML layout matches the newsletter shell (`lib/transactional-email/email-layout.ts`: Inter/Lexend, `#eff1f5` / `#051537`, hero + logo from `GUAPO_EMAIL_ASSET_BASE`); admin invite mail uses the same shell.
- **Member auth + account summary flow (M11):** Auth UX now keeps origin-page redirects across modal/login/Google callback using safe `returnUrl` propagation (`AuthModal` -> `LoginForm`/`RegisterForm`, plus cart/checkout/account gates). New backend endpoint `GET /store/account/summary` provides account dashboard data (customer basics, order/subscription counters, preferred pickup, masked card snapshot). Orders APIs expose optional PDF document URLs; storefront account orders/detail pages render download links only when available.
- **Preferred pickup on account (M11):** `customer.metadata.preferred_pickup_point` stores `{ id, name, address, zipcode, city, carrier_code? }` (merge with existing metadata on save). Account addresses UI reuses checkout `PickupPointSheet` + multi-carrier `fetchAllPickupPoints` via `useAccountPickupSheetSearch` (optional sheet props: no `getOptionForCarrier`, async `onConfirmSelection`). `GET /store/account/summary` prefers profile metadata for `preferred_pickup`, then subscription `delivery_data`, then recent order shipping method data; response includes optional `carrier_code` (gls/dao/pdk). Storefront `formatPickupCarrierLabel` maps to GLS / DAO / PostNord for addresses card + overview (legacy saves without `carrier_code` show no carrier until user re-confirms pickup).
- **Account overview data source fix (M11):** Server-rendered account overview could show empty placeholders because auth state is primarily client-side in this stack. `apps/storefront/src/app/[locale]/account/page.tsx` now delegates to `components/account/AccountOverviewClient.tsx`, which fetches `GET /store/account/summary` from the browser via Medusa client (with credentials), then renders metrics/pickup/card data plus mobile-first cards and error/retry state.
- **Account overview layout (M11):** `AccountOverviewClient` uses a responsive grid: on large screens, **activity** (clickable order/subscription metric tiles → routes) sits beside **account** (profile, pickup, card with inline link CTAs); stacked on small screens. No separate bottom «Mere» link grid. Section CTAs use `Link` + `buttonVariants` (project `Button` has no `asChild`). Footer social icons: `SocialIconComponent` allows `size?: number | string` for Lucide/simple-icons assignability.
- **Orders/subscriptions auth-context fix (M11):** `account/orders` and `account/subscriptions` had the same mismatch (server fetch vs client auth) and could show empty data for logged-in users. Pages now delegate to client components (`components/account/AccountOrdersClient.tsx`, `components/account/AccountSubscriptionsClient.tsx`) that fetch `/store/orders` and `/store/subscriptions` from the browser with credentials, preserving existing status/action UI while ensuring data reflects the active logged-in profile.
- **Account subscriptions list + detail panel (M11):** `AccountSubscriptionsClient` mirrors orders list chrome (gradient container, `divide-y`, monospace id, status pill, **Se detaljer** → `SubscriptionDetailPanel`). Panel uses the same Dialog/Sheet split as `OrderDetailPanel` with solid `bg-background`, fetches `GET /store/subscriptions/:id`, and embeds `SubscriptionActions` (`showViewDetailsLink={false}`, `layout: "stacked"`, `onActionSuccess` + silent list refetch). Subscription mutations POST via `medusa.client.fetch` (publishable key + cookies). Full route `/account/subscriptions/[id]` remains for deep links and still shows actions with **Se detaljer** link when applicable.
- **Store subscription detail payload (M11):** `GET /store/subscriptions/:id` returns `lines[]` (product/variant titles, thumbnail, qty, unit/line totals from initial `metadata.order_id` line matching `variant_id`, else catalog titles only) and `orders[]` (linked renewal orders + initial order, totals in major currency, document PDF flags/URLs). Shared `flattenOrderItemFromGraph` / `resolveLineTotalMajor` live in `apps/commerce/src/lib/store-order-graph-item.ts` (also used by `GET /store/orders/:id`). Panel navigation: root → **Se ordrehistorik** → order list → nested order uses exported `OrderDetailBody` + same labels as account orders.
- **Account list loading (storefront):** `components/ui/skeleton.tsx` + `components/account/AccountListSkeletons.tsx` (`AccountOrdersListSkeleton`, `AccountSubscriptionsListSkeleton`) mirror the gradient list chrome; `AccountOrdersClient` / `AccountSubscriptionsClient` show these instead of plain text while fetching. `sr-only` + `role="status"` carries the loading message for assistive tech.
- **Account status pills (storefront):** Single source `apps/storefront/src/lib/account-status-labels.ts` — `ORDER_STATUS_LABELS` / `SUBSCRIPTION_STATUS_LABELS`, defaults, `getOrderStatusPill` / `getSubscriptionStatusPill`. Used by `AccountOrdersClient`, `AccountSubscriptionsClient`, `OrderDetailPanel`, `SubscriptionDetailPanel`, and `account/subscriptions/[id]/page`.
- **Subscription linked orders (store API):** `GET /store/subscriptions/:id` only includes orders where `customer_id` matches the authenticated customer: graph includes `orders.customer_id`; rows with wrong customer are dropped; missing `customer_id` on link rows are verified via `query.graph` on `order` with `{ id: [...], customer_id }` (batch), with per-id fallback if batch fails. `customer_id` is stripped from the JSON payload (`toPublicLinkedOrder`). Initial order from `metadata.order_id` still requires the same ownership check.
- **Account orders detail totals (M11 debug):** In `GET /store/orders/:id`, `query.graph` order-level `total/raw_total` can be misleading for subscription renewals; use `summary.current_order_total` as primary order total fallback. For items, graph rows can expose `unit_price` while `total/raw_total` is `0`; backend now computes line total as `explicit_total > 0 ? explicit : unit_price * quantity`. Route fetches both direct `items.*` and nested `items.item.*`/`items.detail.*`, flattens shape, and returns major DKK values for stable modal rendering.
- **Order detail modal hardening (M11):** `GET /store/orders/:id` now also requests `items.id` to avoid missing identifiers and derives `shipping_total` when direct shipping amount is `0`/missing: `max(order.total - itemsSubtotal, 0)` (rounded to 2 decimals). Storefront `OrderDetailPanel` uses fallback row keys (`id || variant/title + index`) to prevent React duplicate-key warnings when backend line IDs are absent on legacy rows.
